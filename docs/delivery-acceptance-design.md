# KeepOn 交付验收设计

## 1. 用户流程

用户在「任务规格」中打开交付验收，为任务逐条定义可执行的检查或人工确认项。保存后生成新版本。用户回到对话，从任务卡片点击「执行并验收」，确认执行指令和规格版本。后端将这次 Run 显式绑定到所选任务及其规格版本。执行结束后，Run Explorer 展示逐项结论、原因和证据。全部通过时，当前任务标记为已完成。

以「生成本周支出汇总」为例，用户可以添加四项条件。

| 验收条件 | 类型 | 用户看到的证据 |
| --- | --- | --- |
| 工作区有 `reports/weekly.json` | 文件存在 | 相对路径、文件大小、检查时间 |
| 已发布的 `weekly.json` 包含周起始日期和数字类型的总金额 | JSON 结构 | 交付物链接、内容哈希。失败时显示字段路径和规则 |
| 本次 Run 发布了 `weekly.md` | 交付物已发布 | 交付物链接、发布与检查时间 |
| 报告解释了金额最高的两项支出 | 人工确认 | 用户打开报告，签收或填写退回原因 |

如果 JSON 中的总金额是字符串，界面显示「运行已结束 · 交付待修正」，并定位到 `/total`。用户选择「继续修正」，输入修正要求并启动新 Run。新 Run 使用当前规格，生成独立报告，旧报告仍可查阅。

该例的 JSON 检查可由表单生成以下规则。日期文字的业务含义可另设人工项。

```json
{
  "id": "weekly-json-shape",
  "label": "周报 JSON 包含周起始日期与数值金额",
  "kind": "json_schema",
  "config": {
    "filename": "weekly.json",
    "schema": {
      "type": "object",
      "required": ["week_start", "total"],
      "properties": {
        "week_start": { "type": "string", "minLength": 1 },
        "total": { "type": "number" }
      }
    }
  }
}
```

## 2. 规格与检查规则

沿用现有 `success_criteria` 文本及 `spec_revision`，增加可选的 `acceptance_checks`。每项有稳定的 `id`、用户可读的 `label`、`kind` 和该类型对应的 `config`。启用验收时，编辑器将现有文字条件带入草稿，默认设为人工确认，用户可逐条改成自动检查。规则全部必选，至少一项才可启用。修改规则时连同目标和约束一起存为新规格版本。

| 类型 | 配置和通过条件 | 边界 |
| --- | --- | --- |
| `file_exists` | 工作区相对路径指向普通文件 | 只证明检查时文件存在。预先存在的文件也会通过。需要证明本次确实交付时，搭配发布检查 |
| `json_schema` | 按精确文件名找到本 Run 发布的文件副本。解析 UTF-8 JSON，并用规格中的 JSON Schema 校验 | 检查受管副本与记录哈希一致。找不到文件、同名匹配超过一份、内容无法解析或不符合结构，均给出具体原因 |
| `artifact_published` | 本 Run 存在符合 `kind` 和精确标识的唯一交付物。文件用完整文件名，URL 用标题 | 文件还须有可读取的受管副本。URL 检查的是发布登记，界面注明链接可达性未检查 |
| `manual` | 用户在对应报告上对该项签收 | 退回须填写原因。签收后保留决定与时间，用户可在后续 Run 上重新验收 |

匹配只使用当前 `run_id`，大小写按完整标识精确匹配。前一 Run 或其他会话中的同名交付物不能满足规则。多条匹配提示用户使用唯一文件名或标题。发布记录的作者自述、模型回复和工具返回文本可以辅助定位，机器结论来自 Host 实际检查。

建议起始限制为每份规格 20 项、单个 Schema 32 KiB、单个待校验 JSON 2 MiB。采用受限的 JSON Schema 规则，优先支持类型、必填、属性、枚举、数组和长度或数值范围。保存时检查规则是否合法，并拒绝引用、正则、自定义扩展及未知关键字。执行时限制文档深度和校验错误条数。工作区路径使用项目现有路径解析边界，额外拒绝绝对路径、越界和链接类路径，覆盖 Windows junction 和 UNC。文件存在检查只取元数据。JSON 检查仅读取 Host 管理的副本，不调用模型、Shell、MCP 或外部网络。

## 3. 绑定与状态

**每个验收 Run 对应一项任务、一份规格和一份报告。** 当前 `active_context()` 可能把多个任务都加入同一 Run 的上下文，`plan_task_id` 也会随新建计划变化。新增显式绑定，以后端校验过的 `task_id` 为准。只有本会话中可执行且启用验收的任务能绑定。启动时核对用户看到的 `expected_spec_revision`，避免用户确认后、真正执行前规格已经变化。同一任务同一时间只允许一个显式绑定的 Run 正在执行。

| 情况 | 报告状态 | 对任务的影响 |
| --- | --- | --- |
| Run 仍在执行 | `running` | 任务继续执行 |
| 正常结束，正在检查 | `queued` / `checking` | 等待检查结果 |
| 自动检查均通过，仍有人工项 | `awaiting_review` | 等待用户逐项确认 |
| 任一规则未通过，或人工退回 | `needs_changes` | 保持可继续修正，展示失败原因 |
| 检查器自身异常，例如读盘被拒绝 | `check_error` | 保留诊断并提供「重试检查」 |
| 自动和人工检查全部通过 | `passed` | 仅当报告仍是当前规格最新提交时，将任务标记 `completed` |
| Run 失败、取消或中断 | `not_evaluated` | 任务未关闭，显示 Run 停止原因 |

单项结果使用 `passed`、`failed`、`pending_review`、`error`。检查器异常与规则失败可以同时展示，报告优先显示检查异常，重试后重新汇总。自动检查全部通过后开放人工签收。人工退回后该报告保留为历史，修正通过新 Run 提交。任务总状态继续沿用现有字段，任务卡显示报告状态作为附加信息。

对启用验收的任务，`task_update` 仍可更新执行进度，但直接设置 `completed` 会返回「请完成交付验收」。已验收任务不能由模型改回进行中。用户编辑已完成任务的规格时开启新一轮，并在界面预告会重新打开任务。旧报告继续显示原规格和原结论。启动新提交会取代旧提交的签收资格，即使新 Run 后来失败。Run 恢复创建新 Run，继承原任务与规格，并要求原 Run 仍是最新提交。若原规格已更新，引导从当前规格启动新执行。恢复后的验收只认可新 Run 发布的交付物，需要时重新发布。

## 4. 持久化与执行时序

新增 `task_run_acceptance` 表，以 `run_id` 为主键，保存 `task_id`、`spec_revision`、每任务递增的提交序号、状态和更新时间。索引用于定位任务的最新报告和待处理报告。报告内容包含检查规则快照、各轮尝试、逐项结果及人工决定。证据记录至少包含 `checked_at`、结果码和简短摘要。有交付物时记录 `artifact_id` 与发布摘要，JSON 检查另存 `sha256`。不存文件正文、JSON 字段值、绝对路径或密钥。现有证据和 Trace 可通过 ID 辅助定位，报告自身保留必要摘要，以便原始证据按既有策略淘汰后仍能读懂。

1. **启动。** 在短事务里检查任务归属、状态、规格版本和并发执行条件，写入消息、Run、现有 Spec 绑定与验收行。执行上下文包含已绑定的检查规则，让 Agent 知道该发布哪些文件。
2. **入队。** 在正常结束的持久化边界，将 Run 完成和报告 `queued` 一起提交。验收使用独立的后台处理器，与已有反思任务分开。失败、取消、中断时把报告标为 `not_evaluated`。持久化终态后才向前端通知。提交后的通知或反思失败独立处理，避免把已入队的 Run 改写为执行失败。
3. **检查。** 处理器原子认领队列记录，锁外读取证据和执行检查，再提交结果。检查使用实际检查时间。遇到重启可重试未提交结果的检查，并保留每次已提交的尝试。启动时将上次遗留的验收 Run 标记为中断，释放执行名额，恢复已入队的检查。不会自动重放 Agent 操作。
4. **归档。** 在同一事务内写入最后一项签收或自动结论，并重新检查 Run 已正常结束、规格仍是当前版本、报告仍是最新提交、任务仍可完成。满足时同时更新任务。所有涉及任务记录的写入使用事务内读写，或使用已有 `revision` 做比较更新，避免步骤更新覆盖验收结果。
5. **重试。** 检查器异常可以通过同一 Run 重试，增加尝试记录。规则不通过需要提交新 Run。签收和重试请求带报告版本，服务端拒绝过期决定。重复发送相同决定返回已提交结果。

检查结果描述的是记录时间点上的证据。工作区文件在之后被修改或删除时，旧报告仍展示当时的检查时间。交付物预览发现副本缺失时，单独提示当前无法打开。

## 5. 桌面交互与接口

- **设置 → 任务 Spec。** 增加启用验收开关、条件列表与按类型显示的配置表单。保存前展示新版本号，提交时同时校验 `expected_spec_revision`。任务首次启用后，首版通过创建新版本调整验收项。
- **对话 → 任务卡。** 「执行并验收」显示目标任务和当前规格，允许补充本次指令。「继续修正」带入失败项摘要，用户确认后发起新 Run。历史签收从任务卡可直达对应 Run。
- **Run Explorer → 交付验收。** 显示规格版本、逐项状态、原因、实际检查时间、预览证据的入口。区分 Run 状态与报告状态。旧版或已被替代的报告可读，隐藏签收和重试操作，并说明当前生效版本。

| 接口 | 用途 |
| --- | --- |
| `conversation.send` 扩展 `acceptance_task_id`、`expected_spec_revision` | 发送一次明确绑定任务的正常执行请求，沿用现有对话和流式事件 |
| `task.spec_revise` 扩展 `acceptance_checks`、`expected_spec_revision` | 保存规格新版本 |
| `acceptance.get(run_id)` | 获取报告、当前可执行操作和证据引用。无显式绑定时返回空 |
| `acceptance.review(run_id, criterion_id, decision, expected_report_version, note)` | 人工通过或退回一项 |
| `acceptance.retry(run_id, expected_report_version)` | 将当前技术失败的报告重新入队 |
| `acceptance.updated` | 提交后推送简要通知，刷新报告、任务列表和运行详情。重连后主动读取 |

**签收权限。** 当前 `/rpc` 接收本地 WebSocket 请求，只有从模型工具表移除签收入口还不足以区分桌面操作与任意本地客户端。首版建议由启动器生成会话凭据，交给 Host 和 Electron 主进程。通过有限的 IPC 方法将上述验收写操作转发到 loopback Host，校验调用来自应用主窗口的可信主帧。凭据只用于认证请求，后端在进入业务逻辑前剥离，不出现在渲染页、日志、模型、工具环境或通知里。启用验收、修改已纳管规格、绑定及恢复验收 Run、人工签收和重试都走此校验。普通 RPC 与 Agent 工具无法写入验收结果。分开启动时需给两端提供同一个临时凭据，缺失时验收写操作明确拒绝。这个边界针对未授权请求，进程与数据目录的宿主机控制权仍属于本地用户。

## 6. 兼容、实施顺序与发布验收

数据库按现有迁移机制做备份并新增表，历史任务与 Run 无需回填。缺少 `acceptance_checks` 的任务沿用原完成行为，历史已完成任务保留原状态。用户为进行中的旧任务显式启用时，以新规格开始纳管。普通聊天、计划模式和自动化不自动生成验收报告。计划接受仍代表同意执行，交付签收在实际执行之后发生。

| 阶段 | 可交付结果 |
| --- | --- |
| 一 · 后端基础 | 规则校验、规格快照、显式绑定、三种自动检查、完成闸门。先用离线数据走通正常与失败流程 |
| 二 · 桌面闭环 | 规格编辑、执行入口、报告、证据预览和受保护的人工签收。能从失败报告发起下一次执行 |
| 三 · 发布验证 | 重启恢复、并发冲突、权限与路径边界、旧数据库升级、Windows 与 macOS 冒烟验证 |

发布前用以下场景验证整条链路。

- **成功与失败。** 自动规则全部通过时只关闭任务一次。JSON 类型错误、缺文件、未发布、同名产物或其他 Run 的产物都不能误通过。界面能定位相应原因和证据。
- **人工决定。** 自动通过加人工待确认时，任务保持未完成。签收最后一项后完成。退回理由可查。模型伪造的通过结果、未认证请求和过期页面都无法关闭任务。
- **版本与并发。** 执行中修改规格，旧报告仍按旧版检查。新 Run 启动后，旧报告不可签收。重复点击、并发签收和步骤更新不会覆盖报告或任务状态。
- **进程退出。** 模拟 Run 已正常结束、检查尚未写入结果时退出。重启后检查继续，工具不重复执行。中断的 Run 不产生通过结论。
- **文件边界。** 覆盖路径越界、符号链接与 Windows junction、损坏或删除的副本、超大或过深 JSON，以及带外部引用的 Schema。
- **历史兼容。** 升级现有数据库后，旧已完成任务仍显示原状态，普通对话和计划执行正常。为旧进行中任务启用验收后，下一次显式执行生成报告。

## 7. 源码落点

- `backend/keepon/tasks.py` 管理规则版本、任务状态写入与完成门槛。
- `backend/keepon/application.py` 接入显式绑定、Run 完成入队、交付物读取和事件通知。
- `backend/keepon/database.py` 负责新增验收表、索引和事务。独立的 `acceptance.py` 执行检查、汇总结果和处理人工决定。
- `backend/keepon/server.py`、Electron 主进程和 preload 负责受保护的桌面写入口。
- `desktop/src/KnowledgeGovernance.tsx` 编辑规则，`desktop/src/App.tsx` 发起执行，`desktop/src/RunExplorer.tsx` 展示验收，`desktop/src/types.ts` 与 `eventInvalidation.ts` 补齐状态类型和刷新。
